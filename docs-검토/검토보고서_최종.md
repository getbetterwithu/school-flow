## 🚨 1. 제출물을 지우는 기능이 앱에 없습니다

### 사실

- API 라우트 12개 **전부 GET/POST.** `DELETE`·`PATCH` 핸들러가 **0개**
- `src/lib/repository.ts`에 **삭제 함수 자체가 없음** (list/find/save/mutate 5개뿐)
- `deleteStored()`는 존재하나 호출부 3곳 전부 **실패 롤백·임시저장 교체용**
- 관리 화면에 삭제 버튼 없음

### 무슨 일이 생기나

교사 12명이 학생 개인정보가 든 문서를 제출합니다. 취합이 끝나고 담당자가 파일을 받아 업무를 마쳤습니다. **그 원본들은 `storage/private/`에 UUID 이름으로 영구히 남습니다.**

지우려면 서버에 들어가 `state.json`을 손으로 편집하고 UUID 파일명을 대조해 삭제해야 합니다. **교사인 담당자가 할 수 있는 일이 아닙니다.**

게다가 재제출은 덮어쓰지 않고 버전이 쌓입니다. **한 사람이 3번 내면 개인정보 파일 3개가 영구 축적됩니다.**

> 실제 시연 데이터 확인: 김민정 교사 = 3분 시연에 **버전 3개**, 22,944바이트 HWPX 3개(전부 같은 크기 = 사실상 중복). 시연 하나로 68KB.

운영 규모 추산: 교사 50명 × 재제출 3회 × 200KB = **요청 1건당 30MB**, 연 50건이면 **1.5GB가 전부 삭제 불가.**

### 법적 문제

개인정보보호법 제21조는 **보유기간 경과·목적 달성 시 지체 없는 파기**를 의무화합니다.
교육청 개인정보 모니터링에서 "파기 기능 없음"은 즉시 지적사항입니다.

### 시연에서 나올 질문

> **"이 파일들 언제 지워지나요?"**

현재 답할 것이 없습니다.

### 💬 제안

1. **관리 화면에 "취합 삭제" 버튼** + `DELETE /api/manage/[id]/[token]` 라우트 ← 가장 시급
   - `deleteStored`는 경로 검증까지 이미 되어 있어 그대로 재사용 가능
   - `runSerial`(직렬 큐)이 이미 있어 동시성 걱정 없음
2. 요청 생성 시 **보관기간 선택**(30/90/180일) + 만료 자동 파기
3. **마감 경과 시 모든 임시저장 파기** (현재 영구 잔존)

**난이도 중, 4~5시간.** 기존 함수(`deleteStored`·`runSerial`·`findManaged`) 전부 재사용.

⚠️ **주의:** 자동 파기를 서버 시작 시 일괄 실행하면 시연 직전 데이터가 날아갈 수 있음. 기본값을 넉넉히 하고 해커톤 중에는 환경변수로 끌 수 있게 할 것.

## 🚨 2. 홈 화면을 아무나 볼 수 있습니다

### 사실

- `src/app/page.tsx`가 `listCollections()`로 **모든 취합 요청**을 렌더링
- **토큰 검증 없음.** 미들웨어도 없음 (`src/middleware.ts` 부재 확인)
- `src/app/requests/new/page.tsx`도 무인증이며 **전체 교사 명단**을 렌더링

### 노출되는 것

주소(`http://192.168.x.x:3000`)만 알면 브라우저로 열립니다:

- 진행 중인 모든 취합 요청 제목
- 마감일, 대상 인원 수
- **제출/미제출 인원 수**

예: *"2026년 개인정보보호 및 정보보안 계획 · 마감 8/31 · 12명 · 3/12 제출"*

### 더 심각한 것

**`+ 새 취합 요청`도 아무나 누를 수 있습니다.**
즉 **학교망의 누구나 학교 이름으로 문서 수집 링크를 발급**할 수 있습니다.

### README의 처리

> "현재 앱 자체에 학교 내부망 IP 차단 기능을 넣지 않았습니다. 운영 시 공유기/방화벽에서 서버 3000번 포트를 교내 대역에만 허용해야 합니다."

→ 이를 **네트워크 문제로 축소**했으나, 실제로는 **교내망 안의 학생·방문자도 전부 접근 가능**하다는 뜻입니다. 학교 Wi-Fi는 학생에게도 열려 있는 경우가 흔합니다.

### 💬 제안

`/`와 `/requests/new`에 최소한의 인증(담당자 공용 비밀번호라도) 추가.
파일 내용은 토큰으로 보호되지만, **"누가 뭘 안 냈는지"도 교직원 관련 정보**입니다.

## ⛔ 3. 교사 명단이 코드에 박혀 있습니다 — 시연 최대 리스크

### 사실

`src/lib/domain.ts` 하단에 교사 12명 하드코딩 (김민정/교무기획부, 박성호/교육연구부 …).

### 왜 1순위급인가

연수에서 다른 학교 선생님이 **"우리 학교로 해볼게요"** 하는 순간 **아무것도 못 합니다.**
취합앱의 본질이 명단인데 그게 고정값입니다.

### 💬 제안

요청 생성 시 명단을 **붙여넣기**로 입력(이름/부서, 줄바꿈 구분) + localStorage에 학교 명단 기억.

- `src/lib/domain.ts`: `parseTeacherRoster(text)` 추가. `src/lib/table.ts`의 zod 검증 패턴 그대로 복사
- `src/app/api/collections/route.ts`: 서버 상수 대조 → 클라이언트가 보낸 명단을 zod 검증 후 저장
- `src/components/request-form.tsx`: 체크박스 위에 붙여넣기 textarea. `toolbox.tsx`의 localStorage 패턴 재사용

**난이도 중하, 3~4시간.**

⚠️ **주의:** `recipientIds`가 서버 상수 대조에서 클라이언트 입력으로 바뀌므로 **반드시 zod 검증.** 이름 길이·인원 상한 필수. 기존 `state.json`은 recipients를 통째로 저장하므로 마이그레이션 불필요.

> "자체 호스팅 전에는 '문서가 외부로 절대 나가지 않는다'고 판단하면 안 됩니다."

### 🔥 추가 발견 — 폐쇄망에서 화면이 무한 정지할 수 있음

`@rhwp/editor` 내부:
```js
await new Promise((resolve) => { iframe.addEventListener('load', resolve, {once:true}) });
```

**타임아웃이 없습니다.** iframe이 로드되지 않으면 이 Promise는 영원히 pending → `setReady(true)`에 도달하지 못해 **화면이 "편집기 준비 중…"에서 무한 정지**합니다. 에러도 안 뜹니다.

(브라우저가 연결 실패 시에도 load를 발화하면 15초 후 에러 박스가 뜨는 경로로 빠집니다. **어느 쪽이 나올지 예측 불가.**)

### 대조 — 나이스 API는 잘 만들어졌음

같은 외부 의존인데 `src/lib/neis.ts`는 8초 타임아웃·2MB 상한·에러코드별 HTTP 매핑이 다 있고, 실패해도 **시간표 페이지만 에러 박스를 띄우고 나머지는 정상 동작**합니다. **한쪽만 방어가 돼 있습니다.**

### 💬 제안 — 가장 가성비 높은 작업

rHWP Studio 정적 파일을 `public/rhwp/`에 self-host하고 `NEXT_PUBLIC_RHWP_STUDIO_URL`을 `/rhwp/`로 변경.
**MIT라서 복사 자유. 반나절.** 그리고 이것이 **이 앱이 폐쇄망에서 돈다는 것을 증명하는 유일한 방법**입니다.

추가로 `createEditor` 호출에 자체 타임아웃 래퍼를 씌워 무한 정지 방지.

### 그런데 현재 UI

```
1단계: [한글 문서 취합]  [엑셀 취합]
2단계:                     └ [웹 표로 입력]  [엑셀 파일로 제출]
```

잘못 고르면 "메신저 파일 뭉치"를 앱 안에서 재현하게 됩니다.

## 6. `.hwp` 업로드 시 안내가 없습니다 — 동작은 옳으나 설명이 없음

> ⚠️ **이 항목은 "결함"이 아니라 "안내 누락"입니다.**
> 초안에서는 결함으로 분류했으나, **HWP를 걷어내고 HWPX로 정규화하는 것이 올바른 방향**이라는
> 조원(현직 교사) 판단에 따라 성격을 재분류했습니다.

### 확인된 동작

**rHWP 자체는 둘 다 지원합니다** (`@rhwp/core` = "HWP/HWPX 파서", `editor`에 `exportHwp()`/`exportHwpx()` 둘 다 존재).
그런데 이 앱은 의도적으로 **HWPX 한쪽만** 씁니다.

| 단계 | `.hwpx` 양식 | `.hwp` 양식 |
|---|---|---|
| 업로드 | ✅ 통과 | ✅ **통과 (경고 없음)** |
| 이름 자동 치환 | ✅ 됨 | ❌ **안 됨** |
| 편집기에서 열기 | ✅ | ✅ (rHWP가 지원) |
| **제출 결과 형식** | `.hwpx` | **`.hwpx`로 정규화** |

**코드 근거**
- `submissions/route.ts`: `const extension = type==="xlsx" ? "xlsx" : "hwpx"` — **원본이 무엇이든 hwpx로 저장**
- `rhwp-editor.tsx`: `exportHwpx()`만 호출 (`exportHwp()`는 존재하나 미사용)
- `template/route.ts`: 치환은 `extname===".hwpx"` 조건부. `personalizeHwpx`는 ZIP(fflate) 전제라 구형 HWP(OLE 복합문서)에 **적용 자체가 불가**

### ✅ 이건 올바른 정책입니다

HWP → HWPX 정규화는 **버그가 아니라 방향성**입니다. 구형 바이너리 포맷을 표준 XML 포맷으로 수렴시키는 것이므로 유지해야 합니다.

→ **`exportHwp()`를 쓰도록 "고치자"는 제안은 하지 말 것.** 후퇴입니다.

### 남는 문제 — 안내가 없다

담당자 입장에서 두 가지가 **설명 없이** 일어납니다:

1. 이름이 왜 자동으로 안 채워지는지 모름
2. `.hwp`를 줬는데 왜 `.hwpx`가 돌아오는지 모름

**둘 다 의도된 동작인데, 안내가 없어서 고장처럼 보입니다.**

### 이게 이론이 아닌 증거

`.data/state.json`의 실제 시연 데이터:
```
"templateName": "33_34_임경분.hwp"
```

**해커톤 시연에서 실제로 `.hwp` 양식을 썼고, 따라서 `{{교사명}}` 자동 치환이 작동하지 않았습니다.** 아무 경고 없이요.

### 💬 제안 — 고치는 게 아니라 알려주기

`.hwp` 업로드 시 안내 한 줄 (난이도 하, 30분):

> *"HWP는 HWPX로 변환되어 제출됩니다. 자동 이름 채우기를 쓰려면 HWPX로 올려주세요."*

### 💡 오히려 시연에서 쓸 말이 됩니다

> **"구형 HWP도 받아서 HWPX로 정규화합니다."**

HWP를 걷어내는 방향이라면 이건 결함이 아니라 **기능**입니다.

### ⚠️ 시연 준비 — 이건 별개로 반드시

**시연 양식은 `.hwpx`로 준비하세요.** `.hwp`로 시연하면 자동 치환(가장 화려한 장면)이 그 자리에서 무음으로 실패합니다.

추가로 — HWPX 치환은 `{{교사명}}`이 XML에서 **연속된 문자열**일 때만 됩니다.
한글이 글자를 여러 노드로 쪼개면(중간에 색·굵기 변경 등) 실패합니다.
**리허설 없이 가지 마세요. 실제 파일로 한 번은 돌려봐야 합니다.**

## 7. 공용 PC에서 남의 문서가 열립니다

### 사실

임시저장 복구 키(`draftKey`)가 **localStorage에 평문 저장**됩니다.
(`school-work-draft:{token}:{teacherId}`)

### 시나리오 — 학교의 표준적 사용 패턴

1. 교사 A가 **교무실 공용 PC**에서 작성 중 임시저장하고 나감
2. localStorage는 그대로 남음
3. 다음 사용자(다른 교사, 방과 후 학생)가 같은 브라우저로 그 제출 링크를 엶
4. **draftKey가 자동 재사용되어 A의 임시저장 문서가 편집기에 그대로 열림**

학생 개인정보가 든 문서가 **아무 확인 절차 없이** 화면에 뜹니다.
XLSX는 더 직접적입니다 — 임시 파일 다운로드 링크가 그대로 렌더링됩니다.

### 💬 제안

- 복구 시 **"○○○님의 임시저장본을 불러올까요?"** 확인 단계 추가, 또는
- `localStorage` → `sessionStorage`로 변경(브라우저 종료 시 키 소멸)

## 8. 임시저장·버전이 무한히 쌓입니다

### 버전

`versions.push()`만 있고 **`splice`·삭제·개수 제한이 코드 전체에 없습니다.**
파일 유형은 매번 새 UUID 파일을 쓰고 **이전 파일은 절대 지우지 않습니다.**

### 임시저장 — 더 나쁨

draft가 지워지는 경우는 딱 둘:
1. 같은 기기에서 새로 임시저장(교체)
2. **최종 제출**

즉 **끝내 제출하지 않은 교사의 임시저장은 영원히 남습니다.** 마감이 지나도 정리되지 않습니다.

게다가 교사가 브라우저를 바꾸거나 캐시를 지우면 새 키가 발급되어 **이전 draft는 고아가 되어 영구 잔존**합니다. 소유자도 담당자도 열 수 없고 지울 수도 없습니다. **아무도 인지조차 못 합니다.**

### 💬 제안

§1의 삭제 기능과 세트로 처리. 마감 경과 시 draft 일괄 파기.

요청을 새로 만드는 것 말고는 방법이 없습니다.

   - `request-form.tsx`의 `CopyField`가 이미 clipboard를 씀 → 그대로 재사용

**난이도 하, 2~3시간.**

## 10. PostgreSQL은 "어댑터만 만들면" 되는 상태가 아닙니다

README는 *"뼈대를 포함했고 어댑터는 다음 단계"*라고 해서 스키마를 갈아끼우면 될 것처럼 읽힙니다.

**실제로는 `src/db/schema.ts`에 웹 표 기능에 필요한 컬럼이 통째로 없습니다:**

- `collections`에 `type` 없음 → document/table/xlsx 구분 불가
- `collections`에 `table`(열 정의) 저장할 곳 없음
- `submission_versions`에 `kind`·`rows` 없음 → **표 제출 데이터를 못 담음**
- `storage_key`가 `.notNull()`인데 표 제출은 `storageKey:""`를 씀

**스키마가 웹 표 기능 추가 전에 만들어지고 갱신되지 않았습니다.**

→ **이걸 모르고 착수하면 담당자가 막힙니다.** 스키마 재설계부터 해야 합니다.

⛔ **다만 이틀 안에는 손대지 마세요** — §13 참조.

## 12. ⛔ 절대 건드리면 안 되는 것

**조장이 의도적으로 내린 판단들입니다. 모르고 "개선"하면 핵심이 무너집니다.**

| 설계 | 왜 그런가 | 바꾸면 |
|---|---|---|
| **제출을 덮어쓰지 않고 버전 축적** | 학교 업무의 **감사 성격**. "내가 낸 건 A인데 왜 B가 갔냐" 분쟁의 증거 | 관리 화면 버전 이력이 무의미해지고, 담당자가 복사해둔 다운로드 링크가 404 |
| **로그인 없음** | **"링크 클릭 → 바로 작성"이 유일한 실질 장점.** 계정 발급하는 순간 메신저보다 번거로워짐 | 시연에서 보여줄 "마찰 없음"이 사라짐. 어설픈 로그인은 보안은 그대로면서 마찰만 증가 |
| **교사는 열을 못 바꿈 (행만 추가)** | `normalizeRows`가 서버에서 강제. 열이 교사마다 다르면 **통합 자체가 성립 불가** | **"12명 것을 한 표로 합친다"는 핵심 가치가 즉시 붕괴** |
| **임의 XLSX 자동 병합 안 함** | 셀 위치·시트 구조가 제출자마다 다름 | **절반쯤 되는 병합기는 조용히 틀린 데이터를 만듦.** 시연 중 잘못 합쳐진 표가 나오면 그 자리에서 신뢰 상실 |
| **임시저장이 기기에 묶임** | 로그인 없는 구조에서 draft를 보호하는 유일한 수단 | draftKey 검사를 빼면 **링크를 아는 누구나 남의 작성 중 문서를 다운로드** 가능 |
| **관리 화면이 draft를 안 보여줌** | 담당자는 "누가 작성 중인지"만 알면 됨. 미완성 문서를 훔쳐보면 안 됨 | 교사들이 "임시저장하면 부장이 본다"고 인식 → **임시저장 기능 자체를 안 씀** |
| **마감 검사가 두 번** | 업로드 중 마감이 지날 수 있음. 두 번째는 직렬 큐 안에서 실행 | "중복이니 지우자"고 제거하면 마감 직후 제출이 통과 |
| **`src/lib/*.test.ts` 9개** | 깨지면 조용히 데이터가 틀어지는 지점만 정확히 겨냥 | 회귀 감지 안전망 상실 |

> **손대기 전 반드시 `npx vitest run`. 0.4초입니다. 빨간불이면 되돌리세요.**

## 13. ⛔ 이틀 안에 하지 말아야 할 것

| 금지 | 이유 |
|---|---|
| **PostgreSQL 어댑터 교체** | `Collection`이 `recipients[].versions[].rows[]`까지 깊게 중첩된 단일 객체. 관계형으로 풀면 4개 테이블 조인 + 트랜잭션 재설계. **여러 명이 작업하는 이틀 동안 저장 계층을 바꾸면 나머지 전부가 블로킹됨.** 교사 50명 규모에서 파일 저장소는 성능 문제 없음 |
| **로그인/SSO** | 인증 인프라 협의 필요. 어설프게 붙이면 **개인정보를 더 위험하게** 만듦(평문 저장, 세션 관리 부재) |
| **임의 XLSX 자동 병합** | 데모에서 제일 멋있어 보이지만, **아무것도 안 하는 것보다 나쁨.** 대신 §5에서 "합치려면 웹 표를 쓰세요"를 명확히 안내하는 게 진짜 해법 |
| **브라우저 내 뷰어 추가** | 폐쇄망 리스크만 키움 |
| **급식·학사일정 API 추가** | 기술적으로는 쉽지만(패턴 재사용 2시간), **"취합앱인데 왜 급식이 있지?"**가 됨. 이틀은 핵심을 뾰족하게 하는 데 써야 함 |

## 15. 서버를 어디서 돌릴 것인가

| | 24시간 | 학교 밖 | 승인 | 비용 |
|---|---|---|---|---|
| A. 담당자 노트북 (현재) | ❌ | ❌ | 없음 | 0 |
| **B. 학교에 남는 PC** | ✅ | ❌ | 없음 | 0 |
| C. 서버실 정식 설치 | ✅ | 정책 따라 | **있음** | 있음 |
| D. 클라우드 | ✅ | ✅ | 있음 | 있음 |

**A·B·C 어느 쪽이든 코드는 안 바뀝니다.** 어느 컴퓨터에서 돌리느냐의 문제일 뿐.
→ **이틀 동안 붙잡고 있으면 손해.** 필요한 건 코드가 아니라 답변:

> "지금은 시연을 위해 노트북에서 돌립니다. 운영에서는 학교에 PC 한 대를 두거나 교내 서버에 올리면 되고, Docker 설정은 이미 준비돼 있습니다."

**B안 부가 이점:** 학교 자산이므로 관리 책임 소재가 명확해집니다.
(담당자 개인 노트북이면 분실·수리·퇴직 시 책임이 애매)

### 코드로 고칠 값어치가 있는 것 — IP 문제

링크에 IP가 박힙니다(`http://192.168.50.54:3000/collect/…`).
와이파이를 다시 잡아 `.77`이 되면 **어제 뿌린 링크가 전부 먹통.** 어느 컴퓨터에서 돌리든 발생.

### ⚠️ 별도 — 직렬 큐는 단일 프로세스 전제

`createSerialQueue()`가 모듈 스코프 변수입니다. 프로세스를 여러 개 띄우면(PM2 cluster 등) **프로세스 간 상호배제가 없어 제출이 조용히 유실됩니다.**
현재 `Dockerfile`은 단일 프로세스라 안전하지만 **우연히 안전한 것**입니다.
→ **"동시 제출에 안전하다"고 일반화하면 안 됩니다.** 최소한 코드에 주석이라도.

## 16. 시연 전략

### 가장 강한 것: **웹 표 취합**

세 유형 중 유일하게 "입력 → 자동 통합"이 끝까지 닫힙니다.

**시연 순서:**
1. 담당자가 열 정의 (글자/숫자/날짜/단일선택, 필수, 순서 이동)
2. 링크 복사
3. 교사 A: 이름 선택 → 행 입력 → **새로고침** → 복구되는 것 시연
4. 교사 B도 제출
5. 담당자: **`통합 XLSX 다운로드` 한 번**
6. 열어보면 — **헤더 고정, 자동필터, 열 너비 자동, 남색 헤더 스타일**까지 적용됨

**6번이 인상 포인트입니다.** "CSV 뱉는 것"과 **"열어서 바로 쓸 수 있는 엑셀"**의 차이는 실무자가 즉시 알아봅니다. 숫자 열은 실제 숫자 타입이라 SUM이 바로 됩니다.

또 하나: **제출 현황 시트**. 취합 결과와 미제출자 명단이 **같은 파일 한 장에** 있습니다.
부장 입장에서 "이거 그대로 교감한테 올린다"가 됩니다.

### 반박하기 어려운 지점

1. **"HWP를 브라우저에서 연다"** — 구글드라이브도 MS365도 못 합니다. "그거 이미 있잖아요"에 대한 가장 강한 답
2. **"작성 중은 보이는데 내용은 안 보인다"** — 코드로 보장되고 화면에 정책을 명시. 대안 어디에도 없는 조합
3. **"제출 이력이 지워지지 않는다"** — 분쟁 시 증거
4. **"테스트가 있고 통과한다"** — 그 자리에서 `npm test` 실행. **0.4초.** 해커톤에서 이걸 보여줄 수 있는 팀은 소수
5. **"서버엔 토큰 해시만 있다"** — `.data/state.json`을 열어 `shareTokenHash`만 있는 걸 보여주면 강력

### 반박당하기 쉬운 지점 — 먼저 인정할 것

| 질문 | 대응 |
|---|---|
| "편집기는 외부 아닌가요?" | **먼저 인정.** "폐쇄망에서는 자체 호스팅으로 전환하며, 그래서 환경변수로 뺐습니다" |
| "링크만 알면 아무나 남의 이름으로?" | 사실. 신뢰 기반 식별의 한계를 먼저 말하고 "교내망 + 256비트 링크 + 적용 전 SSO" |
| "저장소가 JSON 파일 하나?" | 사실. 단 원자적 쓰기 + 직렬 큐 + Docker 준비를 보여주면 "설계는 됐고 어댑터만 남았다" |
| **"이 파일들 언제 지워지나요?"** | **현재 답 없음. §1이 1순위인 이유** |

## 17. ❓ 미해결 — 나이스 신규 시스템과의 중복

조원(현직 교사)이 나이스에 새로 들어온 시스템을 언급 — "조사·파일 제출을 간소하게 만든 플랫폼", 과거 **자료집계시스템**의 후신으로 추정. 호칭: "교데통" 또는 "교육데이터통계시스템"(정확한 명칭 미확인).

**여러 키워드로 검색했으나 특정하지 못했습니다.** 잡힌 것은 전부 성격이 다른 시스템(교육행정데이터통합관리시스템, EDSS, KESS — 전부 통계·연구용).
**추측으로 단정하지 않고 미확인으로 남깁니다.**

### 확인된 것 — 구 자료집계시스템 비교

| | 자료집계시스템 | school-flow |
|---|---|---|
| 조사 생성 | 교육청 담당자 | 학교 담당 교사 |
| **범위** | **교육청 → 학교** | **학교 내부** |

매뉴얼: *"기관 소속 사용자 모두에게 보여지고, 제출자가 저장하는 순간 담당자가 자동 지정"* — **학교 단위로 하나 제출**하는 구조. 층위가 다릅니다.

### 확인 필요 — 이 하나로 판가름

> **그 시스템으로 "우리 학교 안에서 교사끼리" 취합이 되나요?**
> 아니면 **교육청이 시킨 것만** 받는 구조인가요?

- 학교 내부 취합이 **된다** → 정면으로 겹침. 시연에서 "그거 나이스에 있잖아요" 한마디에 무너짐
- **교육청 것만** 받는다 → 학교 내부는 빈자리. 이 앱의 존재 이유 확실
