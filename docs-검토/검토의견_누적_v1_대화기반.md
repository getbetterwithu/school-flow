## 1. [구조] 담당자 컴퓨터가 서버인 구조 — 가장 큰 논점

### 현재 상태

실행하면 이렇게 뜹니다:

```
- Local:   http://localhost:3000
- Network: http://192.168.50.54:3000
```

즉 **담당 교사의 노트북이 곧 서버**이고, 다른 교사들은 학교 인트라넷에서 그 주소로 접속합니다. 제출 파일도 담당자 컴퓨터(`storage/private/`)에 쌓입니다.

이 선택 자체는 합리적입니다 — 전산실 서버 구축, 교육청 승인 절차를 통째로 건너뛸 수 있으니까요.

### 걸리는 지점 4가지

1. **담당자가 노트북을 닫으면 앱이 죽습니다.** 퇴근 후 교사가 제출하려 해도 링크가 안 열립니다.
2. **IP가 바뀌면 뿌린 링크가 전부 죽습니다.** `192.168.50.54`는 고정이 아니라, 와이파이를 다시 잡으면 달라질 수 있습니다.
3. **학교 와이파이 밖에서는 접속 불가.** 집에서도, 스마트폰 LTE로도 안 됩니다.
4. **방화벽에 막힐 수 있습니다.** README에도 "macOS 방화벽에서 Node의 수신 연결을 허용해야 할 수 있다"고 적혀 있고, 학교 네트워크가 기기 간 통신을 차단해두면 아예 동작하지 않습니다.

### 조장은 이미 알고 있는 것으로 보임

`compose.yaml`, `Dockerfile`, PostgreSQL 스키마(`src/db/schema.ts`)가 이미 들어 있고, README에도 명시돼 있습니다:

> "현재 하루 시연본의 실행 저장소는 로컬 파일 방식이며 PostgreSQL 저장소 어댑터는 다음 단계입니다."

→ **알고 미뤄둔 것.** 그래서 이건 "왜 안 했냐"가 아니라 "시연 때 이 질문 나오면 어떻게 답할지"의 문제입니다.

### 어디서 돌릴 것인가 — 선택지 4가지

| | 24시간 | 학교 밖 접속 | 승인 절차 | 비용 |
|---|---|---|---|---|
| A. 담당자 노트북 (현재) | ❌ | ❌ | 없음 | 0 |
| **B. 학교에 남는 PC 한 대** | ✅ | ❌ | 없음 | 0 |
| C. 학교 서버실 정식 설치 | ✅ | 정책에 따라 | **있음** | 있음 |
| D. 클라우드 | ✅ | ✅ | 있음 | 있음 |

- **A** — 취합 기간이 하루이틀로 짧으면 실제로 이걸로 충분함.
- **B** — 가장 현실적. 24시간 살아있고, IP를 고정하면 링크도 안 죽음. 학교에 안 쓰는 PC는 대개 있음.
  **부가 이점: 학교 자산이므로 관리 책임 소재가 명확해짐** (아래 10번 참조).
- **C** — 제대로 된 운영이지만, 이 앱이 피하려던 승인 절차가 다시 생김. `Dockerfile`·`compose.yaml`은 이미 준비돼 있음.
- **D** — **앱의 존재 이유를 부정**하므로 제외.

### ⭐ 핵심 — 이건 지금 고칠 문제가 아님

**A·B·C 어느 쪽이든 코드는 하나도 바뀌지 않습니다.** 어느 컴퓨터에서 돌리느냐의 문제일 뿐.
지금 만든 앱 그대로 남는 PC에 넣으면 B, 서버실에 넣으면 C가 됩니다.

→ **금~토에 붙잡고 있으면 손해.** 필요한 건 코드가 아니라 **답변**입니다:

> "지금은 시연을 위해 노트북에서 돌리고 있습니다. 실제 운영에서는 학교에 PC 한 대를 두거나 교내 서버에 올리면 되고, Docker 설정은 이미 준비해뒀습니다."

조장이 `Dockerfile`을 미리 만들어둔 것이 정확히 이 답을 위한 준비로 보입니다.

### 다만 코드로 고칠 값어치가 있는 것 — IP 고정 문제

교사에게 주는 링크에 IP가 그대로 박힙니다:

```
http://192.168.50.54:3000/collect/abc123...
```

와이파이를 다시 잡아 `.77`이 되면 **어제 뿌린 링크가 전부 먹통**입니다.
어느 컴퓨터에서 돌리든 발생하므로, 이건 배치 문제가 아니라 실제 결함.
→ 금~토에 조장과 함께 확인해볼 만한 항목.

### 💬 물어볼 질문

> "담당자 컴퓨터를 서버로 쓰는 구조인데, 노트북이 닫히거나 IP가 바뀌면 링크가 죽습니다. 시연에서 이 질문이 나오면 어떻게 답하기로 하셨어요?"

## 2. [UX] 메뉴 6개 중 2개가 빈 링크

사이드바 구성:

| 메뉴 | 상태 |
|------|------|
| 통합 대시보드 | ❌ `href="#"` — 눌러도 반응 없음 |
| 시간표 | ✅ 구현됨 |
| 업무 취합 | ✅ 구현됨 (앱의 본체) |
| 나의 툴박스 | ✅ 구현됨 |
| 자료실 | ❌ `href="#"` — 눌러도 반응 없음 |
| 업무 매뉴얼 | ✅ 구현됨 |

특히 **`통합 대시보드`가 사이드바 맨 위**에 있습니다. 시연에서 심사위원이 가장 먼저 누를 자리인데 아무 반응이 없으면 첫인상이 나빠집니다.

### 💬 제안

구현하거나, 시연 전까지 메뉴에서 잠시 감추거나 — 둘 중 하나. **감추는 쪽이 비용은 훨씬 싸고 인상은 더 좋습니다.**

## 3. [확장성] 교사 명단이 코드에 하드코딩

`src/lib/domain.ts` 안에 교사 12명이 직접 박혀 있습니다:

```
김민정/교무기획부, 박성호/교육연구부, 이수진/학생생활부 ...
```

다른 학교에서 쓰려면 **코드를 고쳐야** 합니다. 교사가 할 수 있는 일이 아닙니다.

### 💬 제안

이미 나이스 개방 API를 시간표에 쓰고 있으니, 교직원 명단도 같은 방식으로 불러오는 게 자연스럽습니다. 그게 무겁다면 최소한 CSV 업로드 정도로 빼는 방법도 있습니다.

*(단, 시연용 프로토타입이라 일부러 고정해둔 것일 수 있음 — 확인 필요)*

## 4. [정책] 마감 시각이 지나면 제출이 완전히 차단됨

`src/lib/domain.ts`의 `assertCollectionOpen()`이 마감 이후 제출을 막고, `CollectionClosedError`를 던집니다.

메시지: *"제출 마감 시간이 지났습니다. 담당자에게 문의하세요."*

### 걸리는 지점

학교 현실에서 마감을 넘기는 사람은 **항상** 있습니다. 그런데 지금은 담당자가 "문의하세요"라는 안내만 받을 뿐, **정작 담당자에게 풀어줄 방법이 없습니다.** 마감일을 고치는 기능이 안 보입니다.

### 💬 제안

담당자 관리 화면에 **마감 연장** 버튼이 있으면 실전에서 훨씬 쓸 만해집니다.

## 5. [보안 — 의도된 선택] 이름 선택 방식의 신원 확인

교사는 로그인 없이 **목록에서 자기 이름을 고르기만** 하면 됩니다. 즉 링크를 아는 사람은 누구나 타인을 사칭해 제출할 수 있습니다.

**이건 조장이 명시적으로 의도한 선택입니다.** README에 직접 적혀 있습니다:

> "이름 선택 방식은 사용성을 위한 신뢰 기반 식별이지 강한 본인 인증이 아닙니다. 실제 민감정보 취급 전 학교 계정 SSO 또는 내부 인증을 추가해야 합니다."

→ **"로그인 넣자"는 제안은 하지 말 것.** 일부러 뺀 것을 되돌리자는 말이 됩니다. 대신 "어디까지가 안전한 사용 범위인지"를 함께 정리하는 방향이 맞습니다.

## 6. [협업] 코드 포맷이 압축돼 있어 공동 작업 시 충돌 위험

파일들이 줄바꿈 없이 한 줄에 여러 문장이 들어간 형태입니다:

| 파일 | 줄 수 | 바이트 |
|------|-------|--------|
| `security.ts` | 4줄 | 355 |
| `page.tsx` | 7줄 | 2,131 |
| `collection-client.tsx` | 10줄 | 3,045 |

### 왜 문제가 되냐면

한 줄이 곧 함수 여러 개라서, **서로 다른 기능을 고쳐도 Git이 "같은 줄 충돌"로 판정**합니다. 여러 명이 동시에 작업하면 병합할 때마다 파일이 통째로 충돌합니다. 코드 리뷰 시 무엇이 바뀌었는지도 diff로 안 보입니다.

### 💬 제안

공동 작업 시작 **전에** Prettier로 포맷을 한 번 정리하고 시작. 한 번 해두면 이후 충돌이 크게 줄어듭니다.

## 7. [협업 준비] 권한과 역할 분담

### 권한

현재는 공개 레포를 clone만 한 상태 = **읽기 전용**. 수정해도 push할 수 없습니다.

- **A안: Collaborator 초대** — 레포 Settings → Collaborators에 계정 추가. 같은 레포에서 브랜치로 협업. *(추천)*
- **B안: Fork + Pull Request** — 권한 요청 없이 지금 당장 가능하지만 절차가 한 단계 늘어남.

### 역할 분담 후보

화면별로 파일이 잘 분리돼 있어 나눠 갖기 좋은 구조입니다:

| 담당 영역 | 파일 | 비고 |
|-----------|------|------|
| 통합 대시보드 | `src/app/dashboard/` (신규) | **비어 있음 — 신규 참여자에게 최적** |
| 자료실 | `src/app/archive/` (신규) | **비어 있음 — 신규 참여자에게 최적** |
| 시간표 | `timetable/page.tsx`, `timetable-view.tsx` | 구현됨 |
| 업무 매뉴얼 | `manuals/page.tsx`, `manual-search.tsx` | 구현됨 |
| 툴박스 | `tools/page.tsx`, `toolbox.tsx` | 구현됨 |

**단, 한 곳은 반드시 겹칩니다** — 새 화면을 사이드바에 연결하려면 모두가 `src/components/app-frame.tsx`를 건드려야 합니다.

→ 조장이 금요일에 **메뉴 링크를 미리 다 뚫어놓으면** 이 충돌이 사라집니다.

`@rhwp/core`, `@rhwp/editor` 모두 **MIT 라이선스**. 사용·수정·재배포·상업적 사용 전부 자유.
의무는 저작권 표시와 라이선스 전문 포함 하나뿐.

- 제작자: Edward Kim (개인) · 저장소: `github.com/edwardkim/rhwp` · 버전 `0.8.4`
- 한컴과 **제휴·후원·승인 관계 없는 독립 오픈소스** (README에 명시). 한컴이 공개한 파일 형식 문서를 참고한 독자 구현체.
- MIT 표준 무보증 조항 — 문서가 깨져도 제작자 책임 없음.

→ **"막 써도 되냐"에 대한 답: 됩니다.**

### 그런데 구조에 모순이 있음

```
NEXT_PUBLIC_RHWP_STUDIO_URL=https://edwardkim.github.io/rhwp/
```

| 앱의 주장 | 실제 |
|---|---|
| "데이터가 학교 밖으로 안 나갑니다, 폐쇄망용" | 한글 편집기는 **외부에서 불러옴** |

조장도 인지하고 README에 경고를 적어둠:

> "현재 설정은 인터넷이 되는 시연 환경용입니다. 완전한 폐쇄망에서는 rHWP Studio 정적 파일을 내부 서버에 자체 호스팅하고 `NEXT_PUBLIC_RHWP_STUDIO_URL`을 그 내부 주소로 바꿔야 합니다. **자체 호스팅 전에는 '문서가 외부로 절대 나가지 않는다'고 판단하면 안 됩니다.**"

### 💬 제안 — 금~토 작업 후보로 적합

MIT라서 rHWP 파일을 그대로 복사해 자체 호스팅해도 됩니다. 주소만 내부로 바꾸면 끝.
**난이도 낮고, 시연에서 가장 아픈 질문을 막아줍니다.**

### 부가: HWPX 치환의 한계도 함께 안내 필요

README 명시 — 한글이 글자를 여러 XML 노드로 쪼개 저장하면(중간에 색·굵기 변경 등) `{{교사명}}` 치환이 실패합니다.
→ **양식을 단순하게 만들어야 작동.** 사용 안내에 이 조건을 넣는 게 좋겠습니다.

## 9. [기능 확장 ⭐] 파일 업로드 취합 — 구글드라이브를 대체할 수 있는 자리

> ※ 현장 검증을 거쳐 후보 4개 중 3개를 걷어내고 1개로 좁힌 항목.
> 나열보다 **하나에 집중된 제안**이 설득력이 높다고 판단.

### 현재 3가지가 커버하는 것

| 유형 | 쓰는 상황 |
|---|---|
| 한글 문서 | 계획서·보고서 — 양식이 정해진 문서 |
| 웹 표 | 명단·현황 — 표로 합칠 데이터 |
| 엑셀 파일 | 복잡한 서식 — 표로 못 만드는 것 |

공통점: 전부 **"정해진 양식의 문서"**. 그 밖의 파일은 받을 수 없음.

### 빠져 있는 것 — 임의 파일 업로드

현재 확장자·MIME 검사로 **HWP/HWPX/XLSX만** 허용. JPG·PNG·PDF 전부 불가.

실제 학교 수요:
- 수업 사진 / 행사 사진
- 연수 이수증 스캔본
- 동아리 활동 결과물
- 각종 PDF (공문·안내장·이수증)

**PDF는 편집이 아니라 업로드 용도이므로 이 항목에 포함됨** — 별도 기능 불필요.

### 💡 핵심 — 지금 이 일은 구글드라이브가 하고 있음

현재 학교 관행:

> "이 링크 들어가서 파일 올려주세요" (구글드라이브 폴더 공유)

**그런데 이건 원래 하면 안 되는 일입니다.** 학생 사진·학부모 연락처가 든 파일이 구글 서버로 나갑니다.
교육청 감사 대상이고, 다들 알면서도 대안이 없어 쓰고 있는 상황.

→ 그래서 이 기능은 *"구글드라이브가 있으니 불필요"*가 아니라
→ **"구글드라이브를 대체한다"**가 됩니다. 앱의 핵심 명분(폐쇄망·데이터 미유출)과 정확히 일치.

### 💬 시연에서 쓸 수 있는 문장

> "지금 다들 구글드라이브에 올리시죠? 그거 사실 개인정보가 밖으로 나가는 겁니다. 이건 학교 안에 남습니다."

### 난이도

기존 업로드 파이프라인(`storage/private`, UUID 저장, 버전 관리, ZIP 다운로드)이 이미 있음.
**확장자·MIME 검사를 완화하고 유형을 하나 추가하는 수준.** 금~토 작업으로 적합.

---

### ❌ 검토했으나 제외한 후보 (현장 검증 결과)

| 후보 | 제외 사유 |
|------|-----------|
| **설문/단순 응답** (참석 여부, 알레르기 조사, 희망 부서) | **쿨메신저 설문이 이미 잘 수행 중.** 다시 만들어도 우위를 설명하기 어렵고, 심사에서 "그거 쿨메신저에 있잖아요" 반박을 받기 쉬움 |
| **PDF 별도 유형** | 편집이 아닌 업로드이므로 위 파일 업로드에 흡수 |
| **확인만 하기 (제출물 없음)** | 쿨메신저 읽음 표시가 대신함. 앱까지 들어와 버튼을 누를 유인이 없음 |

> 참고 — "학교업무 한곳"이라는 이름과의 긴장:
> 설문은 쿨메신저, 파일은 구글드라이브, 문서 취합은 이 앱 → **여전히 세 군데.**
> 다만 이미 잘 돌아가는 도구까지 흡수하려 들면 범위만 커지고 설득력은 떨어짐.
> **구글드라이브 대체는 "개인정보"라는 명분이 있어 예외로 다룰 가치가 있음.**

---

### ⚠️ 별개 이슈 — 유형 선택 화면이 이미 헷갈림

현재도 `엑셀 취합 → 웹 표로 입력` vs `엑셀 취합 → 엑셀 파일로 제출` 은 처음 보면 구분이 어렵습니다.
유형을 늘릴수록 **"뭘 골라야 하지" 화면**이 되어, 빠르게 하려고 만든 앱이 선택 단계에서 막히는 역설 발생.

**💬 제안 — 질문을 시스템 관점에서 사용자 관점으로:**

- 현재: *"어떤 취합 유형인가요?"*
- 제안: *"교사에게 뭘 받으시겠어요?"*
  - 문서 → 양식 올리기
  - 데이터 → 표 만들기
  - 파일 → 그냥 받기 ← 신규

3개여도 고민이 안 됩니다. 질문이 사람 말이라서요.

## 10. [개인정보 ⭐⭐] 보관 기간과 삭제 정책이 없음 — 가장 시급

> 이 항목은 "교육청이 학교 PC를 다 들여다보는데 서버에 올리는 건 괜찮냐"는 질문에서 출발해 도달한 결론.
> **현재까지 나온 것 중 가장 실질적인 결함.**

### 확인된 사실 — 파일이 계속 불어남

README 명시:

> "최종 제출하면 기존 제출을 **덮어쓰지 않고 새 버전으로 저장**합니다."

즉 교사 1명이 3번 고쳐 내면 파일 3개가 남습니다. 30명이 평균 2번이면 **60개.**
여기에 임시저장본까지 별도로 쌓입니다.

**단, 버전 보관 자체는 좋은 설계입니다.** 취합 현장에서는 "김 선생님이 처음 낸 게 뭐였죠?" 같은 상황이 실제로 생기고, 덮어쓰면 확인할 방법이 없습니다. → **없애자고 제안하면 안 됨.**

### 진짜 문제 — 지울 방법이 없음

문제는 "남기는 것"이 아니라 **"안 지우는 것"**입니다.

- 코드에 **삭제 기능이 없음**
- 손으로 지우려 해도 파일명이 전부 UUID(`a3f2b1c8-…`)라 **뭐가 뭔지 식별 불가**
- 취합이 끝나고 1년 뒤에도 그대로 남음
- 담당자가 바뀌면 전임자 노트북에 계속 남음

### 결과적으로 생기는 상황

이 앱을 쓰면 **담당자 컴퓨터 한 대에 전교생 개인정보가 뭉칩니다.** 원래 흩어져 있던 것이 한곳에 모이는 것.

그리고 그 PC는 **교육청 개인정보 모니터링 대상**입니다.

- 검사에서 "이 PC에 개인정보 파일 수십~수백 개" → 담당 교사가 소명해야 함
- 담당자 **개인 노트북**이면 학교 자산이 아니므로 관리 책임 소재도 애매
  (분실 시? 수리 맡길 때? 퇴직하면?)
  → **1번의 B안(학교 소유 PC)이 여기서 다시 답이 됨**

### 한 문장 요약

> 이 앱은 개인정보를 **밖으로 안 내보내는 데는 성공**했는데, **안에서 관리하는 장치가 아직 없습니다.**

### 💬 시연에서 반드시 나올 질문

> **"이 파일들 언제 지워지나요?"**

현재는 답할 것이 없습니다. 개인정보를 다루는 시스템이면 피할 수 없는 질문입니다.

### 💬 제안 (난이도 순)

1. **취합 완료 시 일괄 삭제 버튼** ← 가장 쉽고 효과 큼. 담당자가 다 내려받은 뒤 누르는 것
2. **보관 기한 표시** — "이 취합은 O월 O일에 정리됩니다"
3. **자동 삭제** — 마감 후 N일 경과 시

**1번만 있어도 답변이 완전히 달라집니다:**

> "취합이 끝나면 담당자가 일괄 삭제할 수 있고, 파일은 학교 안에만 있습니다."

→ **금~토 작업 후보 1순위로 제안할 만함.** 난이도 대비 신뢰도 상승폭이 가장 큼.

## 11. [개념 정리] "교육청이 다 보는데 왜 구글은 안 되나" — 성격이 다름

검토 중 나온 질문에 대한 정리. **시연에서 반박당하지 않으려면 이 구분이 필요합니다.**

### 교육청 모니터링 vs 구글드라이브

| | 교육청 검사 | 구글드라이브 |
|---|---|---|
| 데이터 위치 | 학교 안 | **국외(미국) 서버** |
| 보는 주체 | **감독 기관** | 외부 사기업 |
| 법적 성격 | **관리·감독 권한** | 제3자 제공 · 국외 이전 |
| 문제 여부 | 정상 | 위반 소지 |

교육청은 개인정보보호법상 학교 개인정보의 **관리·감독 주체**입니다. 애초에 그러라고 있는 권한이라, "본다"는 사실 자체가 유출이 아닙니다.

→ 이 앱의 "학교 안에 남는다"는 주장은 **교육청 눈을 피하겠다는 뜻이 아니라, 외부로 안 나간다는 뜻.** 모순이 아님.

### 학교 PC도 해킹당하지 않나 — 맞지만 위험의 종류가 다름

| | 구글드라이브 | 학교 PC |
|---|---|---|
| 접근 경로 | **인터넷 전체** | 학교 내부망 |
| 잠재적 공격자 | 전 세계 누구나 | 학교망에 들어온 사람 |
| 링크 유출 시 | 밖에서 즉시 열람 | 학교 안에 있어야 열람 |
| 방어 역량 | 구글(강함) | 학교(약함) |

- 이 앱은 인터넷에 노출돼 있지 않음 → 공격하려면 **먼저 학교 네트워크 안으로** 들어와야 함. 이 장벽이 실질적으로 큼.
- 반면 구글드라이브 링크는 **주소만 알면 지구 반대편에서도 열림.** 학교 사고의 대부분이 "링크 잘못 공유".
- **단, 학교는 보안 인력이 없음.** 학교망이 뚫리면 방어가 없음.

→ **정확한 표현은 "더 안전하다"가 아니라 "위험의 종류가 다르다".**
시연에서 "무조건 안전하다"고 말하면 반박당합니다. 위 구분으로 답하는 게 정확합니다.

## 12. [확인 필요 ❓] 나이스 신규 시스템과의 중복 여부 — **미해결**

### 상황

조원(현직 교사)이 나이스에 새로 들어온 시스템을 언급 — "조사하거나 파일을 제출하는 것을 상당히 간소하게 만들어놓은 플랫폼", 과거 **자료집계시스템**의 후신으로 추정.
호칭: "교데통" 또는 "교육데이터통계시스템"(정확한 명칭 미확인).

### 검색 결과 — 확인 실패

여러 키워드로 검색했으나 **해당 시스템을 특정하지 못했습니다.** 잡힌 것은 전부 성격이 다른 시스템:

| 검색된 것 | 실제 성격 |
|---|---|
| 교육행정데이터통합관리시스템 | 데이터 수집·분석 플랫폼 (교사 제출용 아님) |
| EDSS(에듀데이터서비스) | 연구자 대상 데이터 제공 |
| 교육통계서비스(KESS) | 학생 수·교원 수 등 통계 |

**추정 원인:** 나이스 로그인 내부 시스템이라 외부 검색에 노출되지 않거나, 최근 도입되어 공개 자료가 아직 없음.
→ **추측으로 단정하지 않고 미확인으로 남김.**

### 확인된 것 — 구 자료집계시스템과의 비교

| | 자료집계시스템 | school-flow |
|---|---|---|
| 조사 생성 | 교육청 담당자 | 학교 담당 교사 |
| 제출 주체 | 학교/교사 | 교사 |
| 파일 첨부 | ✅ | ✅ (한글·엑셀만) |
| 제출 현황 | ✅ | ✅ |
| **범위** | **교육청 → 학교** | **학교 내부** |

매뉴얼 확인 내용: *"기관 소속 사용자 모두에게 보여지고, 제출자가 저장하는 순간 담당자가 자동 지정된다"* — **학교 단위로 하나 제출**하는 구조.

→ 자료집계시스템은 **교육청↔학교** 사이. school-flow는 **학교 안 교사끼리.** 층위가 다름.

### ⚠️ 이 항목이 중요한 이유

- 신규 시스템이 **학교 내부 취합까지 커버한다면** → 이 앱과 정면으로 겹침. 시연에서 "그거 나이스에 있잖아요" 한마디에 무너짐.
- 여전히 **교육청↔학교만** 다룬다면 → 학교 내부는 빈자리. 이 앱의 존재 이유가 확실해짐.

### 💬 확인해야 할 질문 (조원이 직접 확인 가능)

1. 나이스 메뉴에 뜨는 **정확한 명칭**
2. **조사를 만드는 주체**가 교육청인가, 학교 담당자인가
3. **⭐ 학교 안에서 교사끼리** 취합이 되는가, 교육청이 시킨 것만 받는가 ← **이 하나로 판가름**

### 💬 조장에게 물어볼 질문

> "나이스 신규 시스템이랑 뭐가 다른지 정리해두셨어요? 심사에서 분명 나올 질문 같은데요."

## 13. [아이디어 · 장기] 통합 대시보드 = 매일 여는 첫 화면

> ⚠️ **지금 할 일 아님.** 내년에 필요하면 검토할 구상 수준. 금요일에 굳이 안 꺼내도 됨.
> 다만 **2번 항목(빈 메뉴)의 판단을 뒤집는 근거**라서 기록해둠.

### 구상

출근해서 열면 각자 자기 페이지에:

- 오늘 시간표 · 급식표 · 시간표 변동 · 학사일정 (공통 정보)
- **"나한테 온 요청 3건"** (개인화)

### 노션 베이스캠프와 역할이 겹치지 않음

| | 노션 베이스캠프 | 이 대시보드 |
|---|---|---|
| 보이는 것 | 모두에게 같은 것 | **나한테 온 것** |
| 갱신 | 수동 작성 | **자동** |
| 성격 | 자료 쌓아두는 곳 | **오늘 할 일 보는 곳** |
| 위치 | 학교 밖 | 학교 안 |

→ **대체가 아니라 병행.** 노션은 자료 보관, 이건 당일 업무 확인.

### 재료가 이미 대부분 있음

| 필요한 것 | 현재 상태 |
|---|---|
| 시간표 | ✅ **이미 구현됨** (나이스 API) |
| 내 요청 개수 | ✅ **데이터 이미 보유** (제출 현황 관리 중) |
| 급식 | 나이스 API — 시간표와 동일 방식 |
| 학사일정 | 나이스 API — 동일 |

새 기능 개발이라기보다 **흩어진 것을 한 화면에 모으는 작업.**

### 세 가지 걱정에 대한 판단

| 걱정 | 판단 |
|---|---|
| 로그인 | **아래 별도 정리 참조** — 대시보드 도입 시에 한해 필요성이 새로 생김 |
| 외부 접속 | **안 여는 게 맞음** — 열면 "학교 안에만 있다"는 정체성이 붕괴. 애초에 시간표·급식·오늘 할 일은 **출근해서 보는 것**이라 집에서 볼 이유가 적음 |
| 보안 | **진짜 논점** — 단, 새 문제가 아니라 **기존 문제의 무게가 커지는 것** |

### ⭐ 핵심 — 앱의 성격이 바뀜

| | 현재 | 대시보드 도입 시 |
|---|---|---|
| 켜두는 시간 | 취합 기간만 | **항상** |
| 접속자 | 요청받은 교사 | **전 교직원, 매일** |
| 꺼지면 | 그 취합만 멈춤 | **전교가 불편** |

→ **"잠깐 쓰는 도구" → "학교 인프라"**로 승격.
→ 그러면 **1번(어디서 돌릴지)과 10번(파일 정리)이 선결 조건**이 됨.

### 🔑 로그인 — 대시보드가 생기면 전제가 바뀜

**현재 구조에서는 정말 불필요합니다.** 링크 자체가 열쇠이기 때문입니다 (256비트 난수 토큰, 서버엔 SHA-256 해시만 저장).

그런데 대시보드는 **링크 없이 그냥 들어오는 화면** — 열쇠가 사라집니다.

| | 현재 (취합만) | 대시보드 도입 시 |
|---|---|---|
| 사용 시점 | 요청 왔을 때만 | **매일** |
| 진입 | 링크가 있어야 함 | **그냥 들어옴** |
| 노출 범위 | 그 취합 하나 | **내 업무 전체** |

→ **로그인이 필요해지는 원인은 대시보드.** 취합 기능만 놓고 보면 지금이 맞음.

#### ⚠️ 말하는 방식이 중요함

| | 반응 |
|---|---|
| ❌ "로그인 넣죠" | 일부러 뺀 것을 되돌리자는 말로 들림 (5번 참조) |
| ⭕ "대시보드를 만들면 링크 없이 들어오는 화면이 생기는데, 그때는 신원 확인이 필요해지지 않을까요?" | **설계를 이해한 상태에서 조건 변화를 짚는 말** |

#### 로그인은 전부 아니면 전무가 아님 — 단계가 있음

| 단계 | 방식 | 무게 | 비고 |
|---|---|---|---|
| 현재 | 이름만 선택 | 없음 | 링크가 열쇠 |
| **+1** | **처음 한 번 선택 후 브라우저가 기억** | **거의 없음** | **툴박스가 이미 이 방식. 대시보드는 이걸로 충분** |
| +2 | 학교 공용 비밀번호 1개 | 가벼움 | |
| +3 | 개인 계정 | 무거움 | **"비밀번호 까먹었어요"를 받아줄 사람이 학교에 없음** |
| +4 | 나이스/학교 SSO 연동 | 매우 무거움 | README가 언급한 장기 과제 |

→ **+3부터가 조장이 뺀 이유.** 관리 주체가 없는 것이 실질적 장벽.
