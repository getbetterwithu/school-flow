> 목적: 원 보고서를 대체하기보다, 동의점·보완점·우선순위 차이를 명확히 정리합니다.

## 1. 총평

Claude 보고서는 **현장 사용자의 질문과 해커톤 시연 실패 지점**을 매우 잘 포착했습니다. 특히 삭제 기능 부재, 고정 교사 명단, 웹 표의 낮은 노출도, 마감 연장 수단 부재, PostgreSQL 스키마 불일치, 비어 있는 메뉴는 실제 발표와 후속 개발에 직접 도움이 되는 지적입니다.

다만 보안 관점에서는 중요한 공격 경로가 일부 빠졌고, 몇몇 우선순위와 표현은 조정할 필요가 있습니다. 가장 큰 차이는 다음과 같습니다.

> 삭제 기능은 매우 중요하지만, 실제 문서를 넣기 전 가장 먼저 막아야 할 것은 **무인증 요청 생성, 제출자 사칭, 무제한 업로드, 외부 rHWP 신뢰 경계**입니다.

삭제는 목적 달성 후의 개인정보 위험이고, 사칭과 무제한 업로드는 서비스가 열려 있는 순간부터 발생할 수 있는 현재형 위험입니다.

종합적으로 Claude 보고서의 완성도는 높습니다. 제품·시연 검토로는 약 **90점**, 보안 검토로는 누락된 공격 표면 때문에 약 **75점**으로 평가합니다.

## 2. 전적으로 동의하는 핵심 지적

### 2.1 제출물 삭제·보존 정책 부재

동의합니다. 현재 요청, 제출 버전, 임시본을 정상적인 UI와 API로 삭제할 방법이 없습니다. `deleteStored()`는 실패 롤백과 임시본 교체에만 사용됩니다.

단순한 삭제 버튼만 추가해서는 부족합니다. 함께 정의해야 할 정책은 다음과 같습니다.

- 취합 요청 전체 삭제
- 특정 제출 버전 삭제 가능 여부
- 감사 목적으로 보존할 버전 범위
- 마감 후 임시본 자동 파기
- 기본 보존기간과 담당자 연장
- 삭제 로그와 실제 저장 파일 정합성
- 백업본의 파기 시점

버전 불변 보관 철학과 개인정보 최소 보존은 충돌할 수 있으므로, “무기한 보관”이 아니라 **정해진 기간 동안 불변 보관**으로 정리하는 것이 적절합니다.

### 2.2 홈·요청 생성 화면 무인증 공개

동의합니다. `/`는 모든 취합 제목·마감·대상 수·제출 수를 공개하고, `/requests/new`와 `POST /api/collections`는 누구나 요청을 만들 수 있습니다.

특히 요청 생성 권한 부재는 정보 노출을 넘어 다음 문제를 만듭니다.

- 학교 명의의 가짜 취합 링크 생성
- 악성 양식 배포
- 서버 저장공간 고갈
- 교직원 대상 피싱

따라서 홈 가리기와 함께 **요청 생성 API 자체의 권한 검사**가 반드시 들어가야 합니다.

### 2.3 교사 명단 하드코딩

동의합니다. 다만 “시연 불가”보다는 **현재 준비된 고정 시연은 가능하지만 다른 학교로 일반화한 즉석 시연이 불가능하다**가 더 정확합니다.

명단 붙여넣기는 해커톤 직전의 현실적인 해법입니다. 운영 단계에서는 CSV/XLSX 가져오기, 학교 계정 디렉터리 연동, 중복 동명이인 처리까지 고려해야 합니다.

### 2.4 rHWP 외부 의존

동의합니다. 외부 GitHub Pages iframe으로 문서 바이트가 전달되므로 폐쇄망·내부 보관 주장과 충돌합니다. 로딩 타임아웃이 불완전하다는 지적도 타당합니다.

다만 자체 호스팅만으로 문제가 모두 해결되지는 않습니다. 현재 `@rhwp/editor`가 생성하는 iframe에는 `sandbox`가 없고 `clipboard-read; clipboard-write` 권한이 부여됩니다. 따라서 다음이 함께 필요합니다.

- Studio 정적 자산 내부 호스팅 및 버전 고정
- 배포 자산 무결성 검증
- CSP의 `frame-src`와 `connect-src` 제한
- 불필요한 클립보드 권한 제거 가능성 검토
- iframe sandbox 적용 가능성 검증
- 편집기 로딩·요청 타임아웃과 실패 복구 UI

### 2.5 웹 표를 핵심 기능으로 전면 배치

동의합니다. 세 유형 중 웹 표만이 입력부터 통합 결과까지 업무를 완전히 닫습니다. 카드 3개를 평평하게 보여주고 결과물을 명시하자는 제안도 좋습니다.

한글 문서 취합의 담당자 측 이득을 높이려면 향후 문서 최신본 일괄 ZIP 다운로드가 필요합니다. 현재 한글 문서는 교사별로 클릭해야 하므로 링크 기반 제출 편의는 있지만 담당자의 수집 노동은 완전히 사라지지 않습니다.

### 2.6 HWP → HWPX 정규화 안내

동의합니다. 변환 방향 자체는 합리적이며, 자동 치환이 HWPX에만 적용되고 결과물이 HWPX가 된다는 사실을 업로드 시점에 명확히 알려야 합니다.

### 2.7 공용 PC의 임시본 자동 복구

동의합니다. 같은 브라우저 프로필을 여러 사람이 사용하는 환경에서는 localStorage의 복구 키가 사실상 다음 사용자에게 문서를 넘겨줍니다.

다만 `sessionStorage`로 바꾸면 브라우저 종료 후 복구라는 핵심 가치가 사라집니다. 추천안은 다음 순서입니다.

1. 복구 전 이름과 부서를 다시 표시하고 명시적으로 확인
2. “이 기기에서 복구 정보 삭제” 기능 제공
3. 복구 키 만료
4. 운영 단계에서는 계정 기반 암호화 복구

### 2.8 PostgreSQL 스키마 불일치

전적으로 동의합니다. 현재 스키마에는 `type`, 표 정의, 제출 `kind`, 표 행 데이터가 없어 단순 어댑터 교체로는 전환할 수 없습니다. README의 “어댑터는 다음 단계”라는 표현은 실제 작업량을 작게 보이게 할 수 있습니다.

### 2.9 비어 있는 사이드바 메뉴

동의합니다. 해커톤 직전에는 빈 기능을 채우기보다 링크를 숨기는 것이 안전합니다.

## 3. 우선순위를 더 높여야 하는 누락 사항

### 3.1 제출자 사칭 — 운영 전 최우선

공용 링크 사용자는 전체 대상자의 이름·부서·제출 횟수를 볼 수 있고, 임의의 `teacherId`로 다른 교사 명의의 제출을 만들 수 있습니다. 재제출도 제한이 없어 정상 제출 뒤에 허위 파일을 추가할 수 있습니다.

Claude 보고서는 로그인 부재를 의도적 판단으로 보호해야 한다고 보지만, **낮은 마찰과 무인증 사칭은 같은 개념이 아닙니다.** 다음과 같은 저마찰 대안이 있습니다.

- 교사별 1회성 또는 만료형 제출 링크
- 학교 계정 SSO
- 이름 선택 후 개인 확인 코드
- 내부 메신저로 발급되는 단기 토큰

즉, 전통적인 아이디·비밀번호 로그인은 피할 수 있지만 제출자 권한 검증 자체를 포기해서는 안 됩니다.

### 3.2 임시본·버전·요청 생성 무제한으로 인한 서비스 거부

현재 rate limit, 사용자별 할당량, 요청당 총 용량, 버전 개수 제한이 없습니다.

특히 임시저장 API는 공격자가 임의 UUID를 계속 바꾸면 같은 대상자 아래에 20MB 임시 파일을 무제한 생성할 수 있습니다. 웹 표도 버전마다 JSON에 누적되고, 저장소는 매 요청마다 전체 `state.json`을 다시 읽고 씁니다.

이는 단순한 개인정보 축적이 아니라 **디스크·메모리·CPU 고갈을 통한 서버 중단 취약점**입니다. 삭제 기능보다 먼저 최소한 다음 방어가 필요합니다.

- IP·토큰별 요청 속도 제한
- 교사별 활성 임시본 개수 제한
- 요청당 전체 저장 용량 제한
- 제출 버전 상한 또는 보존 정책
- 전체 서버 여유 공간 감시
- 요청 생성 권한 제한

### 3.3 HWPX 압축 폭탄

`personalizeHwpx()`는 HWPX 전체를 `unzipSync()`로 메모리에 풉니다. 업로드 파일이 20MB 이하더라도 압축 해제 결과는 수 GB가 될 수 있습니다.

현재 압축 해제 크기, 항목 수, 개별 XML 크기 제한이 없습니다. 무인증 요청 생성과 결합하면 원격 메모리 고갈 경로가 됩니다.

필요한 방어는 다음과 같습니다.

- HWPX ZIP 구조 사전 검증
- 압축 해제 총량과 파일 개수 상한
- 개별 XML 크기 상한
- 동기식 전체 압축 해제 회피
- 별도 작업 프로세스와 시간·메모리 제한

### 3.4 파일 내용 검증과 악성 문서 유통

HWP/HWPX는 확장자만 검사하고 XLSX는 MIME 및 `PK` 시작 바이트만 확인합니다. 임의 파일 또는 악성 ZIP을 정상 문서처럼 저장하고 담당자에게 다운로드시킬 수 있습니다.

서버에서 실행되지 않는다고 안전한 것이 아닙니다. 담당자가 한글이나 Excel에서 파일을 열기 때문에 이 앱은 악성 문서의 전달 통로가 될 수 있습니다.

파일별 구조 검증, 다운로드 시 `attachment`와 `nosniff`, 악성코드 검사, 운영체제 격리 저장을 고려해야 합니다.

### 3.5 URL 기반 비밀정보 노출

관리 토큰과 제출 토큰은 URL 경로에 있고 임시 복구 키는 쿼리 문자열에 있습니다. 이 값들은 브라우저 기록, 프록시·서버 로그, 화면 공유, 복사 기록, Referer에 남을 수 있습니다.

특히 관리 페이지에서 같은 origin의 다른 페이지로 이동하면 전체 관리 URL이 Referer로 기록될 가능성이 있습니다. 관리 토큰은 최초 교환 후 `HttpOnly`, `Secure`, `SameSite` 세션 쿠키로 전환하고 URL에서는 제거하는 편이 안전합니다.

### 3.6 마감 후 임시저장 허용

최종 제출은 마감을 두 번 확인하지만 파일·표 임시저장은 마감을 확인하지 않습니다. 마감 이후에도 저장공간 소비와 “작성 중” 상태 조작이 가능합니다.

마감 정책이 제출만 막는 것인지 모든 작성을 막는 것인지 제품 정책을 명확히 하고, 후자라면 모든 쓰기 API에 동일한 검사를 적용해야 합니다.

### 3.7 HTTPS와 보안 헤더

현재 실행 안내는 HTTP 기반이며 `next.config.ts`에 CSP, Referrer-Policy, frame 제한, HSTS, 전역 `nosniff`가 없습니다. 내부망에서도 토큰과 문서가 평문으로 오가므로 HTTPS는 운영 전 필수입니다.

## 4. 조정하거나 반론이 필요한 주장

### 4.1 “로그인 없음은 절대 건드리면 안 된다”

해커톤 시연 전략으로는 이해하지만 운영 원칙으로는 동의하기 어렵습니다. 현재 모델은 사용 편의가 아니라 **명의 도용을 허용하는 신뢰 기반 식별**입니다.

추천하는 표현은 다음과 같습니다.

> 무거운 계정 발급 방식은 피하되, 제출자별 단기 링크나 학교 SSO로 저마찰 신원 검증을 추가합니다.

### 4.2 “삭제 기능이 무조건 1순위”

개인정보 운영 준비에서는 최상위 항목이 맞습니다. 그러나 공격 가능성과 피해 발생 시점을 기준으로 하면 다음 순서가 더 안전합니다.

1. 요청 생성 권한과 제출자 사칭 차단
2. 외부 rHWP 격리 또는 자체 호스팅
3. 무제한 업로드·압축 폭탄 차단
4. 삭제·보존 정책

### 4.3 “교사 명단 하드코딩은 시연 불가”

준비된 12명으로 하는 고정 시연은 가능합니다. 문제는 현장 참가자가 자기 학교 명단으로 즉석 체험하거나 제품을 재사용할 수 없다는 점입니다. “제품화·확장 시연 불가”가 더 정확합니다.

### 4.4 “서버 위치만 바뀌며 코드는 안 바뀐다”

단순 시연에서는 맞지만 24시간 운영에서는 달라집니다.

- HTTPS와 인증서
- 고정 도메인
- 프록시 신뢰 설정
- 백업·복구
- 자동 파기 작업
- 감사 로그
- 프로세스 재시작
- 비밀정보 관리
- 저장소 트랜잭션

등이 필요하므로 배포 형태는 코드와 운영 설계에 영향을 줍니다.

### 4.5 개인정보보호법 단정

목적 달성 후 불필요한 개인정보를 계속 보관해서는 안 된다는 방향에는 동의합니다. 다만 구체적인 법적 의무와 적용 예외, 학교 기록물 보존 의무의 충돌은 기관 담당자나 법률·개인정보 책임자의 확인이 필요합니다. 보고서에서는 법률 자문처럼 단정하기보다 “운영 전 기관 정책 및 법적 검토 필요”로 표현하는 편이 안전합니다.

### 4.6 “README 기술적 주장은 전부 일치”

대체로 잘 일치하지만 “전부”라는 표현은 강합니다. 예를 들어 PostgreSQL 전환 준비도는 스키마가 현재 도메인을 담지 못하고, 운영 안전성은 별도 검증이 필요합니다. “확인한 핵심 기능 설명은 대체로 코드와 일치한다”가 더 정확합니다.

- `npm run build`: 현재 검토 환경에서는 Turbopack이 CSS 처리용 내부 프로세스의 포트 바인딩에 실패

Claude 보고서의 별도 clone 환경에서는 빌드가 성공했으므로, 이것은 확정된 코드 결함이라기보다 **환경 의존 빌드 문제**로 보는 것이 타당합니다. 다만 현재 작업환경에서 재현되므로 `turbopack.root` 경고와 함께 별도 확인이 필요합니다.

### 5.2 의존성 감사

온라인 `npm audit`에서 moderate 6건, high/critical 0건이 확인됐습니다.

- `drizzle-kit` 하위 구버전 `esbuild`
- `exceljs` 하위 구버전 `uuid`

특히 esbuild 권고는 개발 서버가 악성 웹사이트의 요청에 노출될 수 있는 유형입니다. 이 프로젝트가 실제 시연에서도 `next dev`를 실행하므로 일반적인 개발 전용 도구보다 주의가 필요합니다.

### 5.3 확인된 긍정적 방어

- 256비트 난수 토큰과 SHA-256 해시 저장
- 제출 토큰과 관리 토큰 분리

- `public` 밖의 비공개 저장소

- 경로 정규식 검사

## 7. 최종 의견

Claude 보고서는 **제품과 현장 시연을 살리는 보고서**로서 강점이 큽니다. 특히 기능을 더 붙이기보다 웹 표를 중심으로 메시지를 선명하게 하고, 빈 메뉴를 제거하며, 삭제·마감·명단이라는 실제 운영 질문에 답하도록 한 방향은 좋습니다.

GPT 교차 검토에서 가장 크게 보완하는 결론은 다음 한 문장입니다.

> SchoolFlow의 철학인 “링크 하나로 마찰 없이 제출”은 유지하되, 링크 소유자가 누구든 모든 교사를 사칭할 수 있는 현재 구조까지 철학으로 보호해서는 안 됩니다.

해커톤에서는 웹 표 취합의 완결성을 중심으로 보여주고, 실제 학교 데이터 투입 전에는 인증·자원 제한·rHWP 내부화·삭제 정책을 하나의 필수 묶음으로 처리하는 것이 가장 안전합니다.
