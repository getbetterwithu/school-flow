## 2. A. 시연 전 — 이틀 안에 (메시지를 뾰족하게)

### 2-1. ⭐ 웹 표를 전면에 배치 — 가장 중요

**세 유형의 실제 차이를 코드로 확인했습니다.**

| 유형 | 담당자 작업량 | 근거 |
|---|---|---|
| **웹 표** | **버튼 1번 → 통합 엑셀 1장** | `xlsx.ts`가 전 교사 rows를 한 시트에 append |
| 엑셀 파일 | ZIP 1번 → **복붙 수작업 그대로** | `download-latest`는 `zipSync` 한 줄. 파일 내용을 **한 바이트도 안 읽음** |
| **한글 문서** | **일괄 다운로드 버튼이 없음** | 교사 수만큼 클릭해야 함 |

**웹 표만이 "여러 스프레드시트를 수작업으로 합치는 흐름"을 실제로 없앱니다.**
한글 문서는 교사 쪽 이득은 크지만(브라우저 편집) **담당자 쪽 이득은 사실상 0**입니다.

**그런데 현재 UI에서 웹 표가 숨어 있습니다:**

```
1단계: [한글 문서 취합]  [엑셀 취합]
2단계:                     └ [웹 표로 입력]  [엑셀 파일로 제출]
```

웹 표는 엑셀이 아닌데 "엑셀 취합" 하위에 있고, 셋 중 가장 가치가 큰 옵션입니다.
그리고 **결과물이 어떻게 나오는지 화면 어디에도 없습니다.** 잘못 고르면 "메신저 파일 뭉치"를 앱 안에서 재현하게 됩니다.

**💬 제안 — 평평한 카드 3장 + 결과물 명시**

```
[웹 표로 받기]              ← 추천
 표 칸을 웹에서 직접 입력
 → 결과: 통합 엑셀 1장 (자동 합쳐짐)

[한글 문서로 받기]
 HWP/HWPX 양식을 브라우저에서 작성
 → 결과: 교사별 한글 파일

[엑셀 파일로 받기]
 XLSX 양식을 Excel에서 작성
 → 결과: 교사별 파일 ZIP (자동 합쳐지지 않음)
```

`request-form.tsx` + `globals.css` 3열 그리드. **서버 무변경. 2~3시간.**
덤: `deadline` 기본값이 없어 매번 손으로 찍어야 합니다 → "3일 뒤 오후 5시" 기본값. **5분.**

### 2-3. ⚠️ HWPX 자동 치환 리허설 — 반드시

**시연 데이터에 사고 흔적이 남아 있습니다.**

`.data/state.json`:
```
"templateName": "33_34_임경분.hwp"
```

자동 치환은 **`.hwpx`에서만** 됩니다(`personalizeHwpx`가 ZIP 전제 → 구형 HWP는 구조가 달라 적용 불가).
**해커톤 시연에서 `.hwp`를 썼고, 따라서 `{{교사명}}` 치환이 작동하지 않았습니다.** 경고도 없이요.

**그리고 `.hwpx`라도 안심할 수 없습니다.** 한글이 `{{교사명}}`을 여러 XML 노드로 쪼개 저장하면(중간에 색·굵기 변경 등) 치환이 실패합니다.

**💬 시연에 쓸 실제 파일로 반드시 한 번 돌려보세요.** 가장 화려한 장면이 무음으로 실패할 수 있습니다.

### 2-5. rHWP 로딩 타임아웃

`@rhwp/editor` 내부:
```js
await new Promise((resolve) => { iframe.addEventListener('load', resolve, {once:true}) });
```

**타임아웃이 없습니다.** iframe이 안 뜨면 이 Promise가 영원히 pending → **화면이 "편집기 준비 중…"에서 무한 정지**합니다. 에러도 안 뜹니다.

(브라우저가 실패 시에도 load를 쏘면 15초 후 에러 박스 경로로 빠집니다. **어느 쪽이 나올지 예측 불가.**)

**대조:** 같은 외부 의존인데 `neis.ts`는 8초 타임아웃·2MB 상한·에러코드별 HTTP 매핑이 다 있고, 실패해도 시간표 페이지만 에러 박스를 띄우고 나머지는 정상입니다. **한쪽만 방어가 돼 있습니다.**

**💬 `createEditor`에 타임아웃 래퍼.** 1~2시간.

## 3. B. 실제 학교 데이터 넣기 전 — 필수 묶음

> **이 묶음은 이틀 작업이 아닙니다.** 다만 **"언제 할지"를 정해두는 것**이 금요일 논의 대상입니다.
> 아래 순서는 **피해가 발생하는 시점** 기준입니다.

### 3-1. 🚨 요청 생성이 무인증입니다 — 지금 열려 있는 문

**사실:**
- `src/app/page.tsx`가 `listCollections()`로 **모든 취합 요청**을 렌더링. **토큰 검증 없음**
- `src/app/requests/new/page.tsx`도 무인증. **전체 교사 명단**을 렌더링
- 미들웨어 없음 (`src/middleware.ts` 부재 확인)

**주소만 알면 학교망의 누구나** — 학생 포함 — 이걸 봅니다:
> *"2026년 개인정보보호 및 정보보안 계획 · 마감 8/31 · 12명 · 3/12 제출"*

**더 심각한 건 `+ 새 취합 요청`도 아무나 누를 수 있다는 것입니다.**
즉 **학교 명의의 가짜 취합 링크를 누구나 발급**할 수 있습니다. 악성 양식 배포·피싱 경로가 됩니다.

README는 *"방화벽에서 3000번 포트를 교내 대역에만 허용하라"*고 하셨는데, **학교 Wi-Fi는 학생에게도 열려 있는 경우가 흔합니다.**

**💬 `/`와 `/requests/new` + `POST /api/collections`에 권한 검사.** 화면만 가리면 안 되고 **API 자체**에 필요합니다.

### 3-2. 🚨 제출자 사칭 — 링크를 아는 누구나

**사실:** 신원 검증의 전부가 `recipients.find(r => r.id === teacherId)`입니다.
`teacherId`는 `t01`~`t12`로 **추측 가능**하고, 제출 페이지가 **전체 교사 명단을 클라이언트로 내려줍니다.**

링크는 단톡방을 거치며 사실상 준공개됩니다. 링크를 얻은 사람이 `t03 이수진`을 클릭하고 파일을 올리면 **이수진 명의로 제출이 기록됩니다.** 재제출 제한도 없어 정상 제출 뒤에 허위 파일을 덧붙일 수도 있습니다.

**💬 여기서 조심스럽게 말씀드립니다**

README에 *"신뢰 기반 식별이지 강한 본인 인증이 아니다"*라고 명시하신 것, 그리고 **"링크 클릭 → 바로 작성"이 이 앱의 핵심 가치**라는 것 — 둘 다 동의합니다. **계정·비밀번호 발급은 하지 말아야 합니다.** 교사 30명에게 계정을 주는 순간 메신저보다 번거로워집니다.

다만 **"마찰이 낮다"와 "사칭이 가능하다"는 같은 것이 아닙니다.**
사이에 저마찰 선택지가 있습니다:

| 방식 | 마찰 | 비고 |
|---|---|---|
| **교사별 개별 링크** | **거의 없음** | 지금과 동일한 경험. 링크만 사람 수만큼 발급 |
| 이름 선택 + 확인 코드 | 낮음 | 4자리 숫자 정도 |
| 학교 SSO | 중간 | 운영 단계 |

**교사별 개별 링크가 가장 자연스러워 보입니다.** 교사 입장에서는 지금과 똑같이 링크 하나 누르는 것이고, 사칭만 막힙니다.

→ **이건 제안이 아니라 질문입니다.** 조장님이 이미 고민하셨을 것 같아서, 어떻게 보시는지 듣고 싶습니다.

### 3-3. 🚨 무제한 업로드 — 서버가 멈출 수 있습니다

**확인한 사실 (코드 전체 검색):**
- rate limit **0건**
- 임시저장 개수 제한 **없음** (`drafts.push()`만 있고 상한 없음)
- 제출 버전 상한 **없음** (`versions.push()`만, `splice` 없음)
- 요청당 총 용량 제한 **없음**

**공격 경로:** 임시저장 API는 `draftKey`(UUID)를 계속 바꾸면 **같은 교사 아래에 20MB 파일을 무제한 생성**할 수 있습니다.

그리고 저장소는 **매 요청마다 `state.json` 전체를 읽고 씁니다.** 디스크가 차면 쓰기가 실패해 **기존 제출 데이터까지 손상**될 수 있습니다.

**💬 필요한 최소 방어:** IP·토큰별 속도 제한, 교사별 활성 임시본 개수 제한, 요청당 총량 제한, 버전 상한.

### 3-4. 🚨 압축 폭탄 (zip bomb)

`personalizeHwpx()`가 HWPX 전체를 `unzipSync()`로 **메모리에 통째로** 풉니다.

**업로드가 20MB 이하여도 압축을 풀면 수 GB가 될 수 있습니다.** 해제 크기·항목 수·개별 XML 크기 제한이 **전부 없습니다.**

그리고 **§3-1의 무인증 요청 생성과 결합하면** 원격에서 서버 메모리를 고갈시킬 수 있는 경로가 됩니다.

**💬 압축 해제 총량·파일 개수 상한, 개별 XML 크기 상한. 동기식 전체 해제 회피.**

### 3-5. ⚠️ rHWP 외부 의존 — 폐쇄망 주장과 충돌

**라이선스는 문제없습니다 (확인 완료).**
`@rhwp/core`·`@rhwp/editor` 모두 **MIT.** 사용·수정·재배포·상업적 사용 전부 자유. 의무는 저작권 표시 포함 하나뿐.
한컴과 제휴·승인 관계 없는 독립 오픈소스(README 명시). 버전 `0.8.4`.

**문제는 구조입니다.**
```js
studioUrl: process.env.NEXT_PUBLIC_RHWP_STUDIO_URL || "https://edwardkim.github.io/rhwp/"
```

GitHub Pages를 iframe으로 로드 → **문서 바이트가 외부 오리진으로 넘어갑니다.**

README에 *"자체 호스팅 전에는 '문서가 외부로 절대 나가지 않는다'고 판단하면 안 된다"*고 정확히 써두셨습니다.

**💬 자체 호스팅 (반나절)** — MIT라 복사 자유. `public/rhwp/`에 넣고 환경변수만 `/rhwp/`로.
**이 앱이 폐쇄망에서 돈다는 것을 증명하는 유일한 방법입니다.**

**⚠️ 다만 자체 호스팅만으로 끝나지 않습니다.** 현재 iframe에는 `sandbox`가 없고 `allow='clipboard-read; clipboard-write'`가 부여돼 있습니다(코드 확인). 함께 필요한 것: CSP의 `frame-src`/`connect-src` 제한, 불필요한 클립보드 권한 제거 검토, sandbox 적용 가능성 검증.

### 3-6. 🚨 삭제·보존 정책 — 목적 달성 후의 위험

**사실 (전수 확인):**
- API 라우트 12개 **전부 GET/POST.** `DELETE`·`PATCH` **0개**
- `repository.ts`에 **삭제 함수 자체가 없음**
- `deleteStored()`는 있으나 호출부 3곳 전부 **실패 롤백·임시본 교체용**
- 관리 화면에 삭제 버튼 없음

취합이 끝나도 **원본이 `storage/private/`에 UUID 이름으로 영구히 남습니다.**
지우려면 서버에 들어가 `state.json`을 편집하고 UUID를 대조해야 하는데, **교사인 담당자가 할 수 있는 일이 아닙니다.**

**임시저장은 더 심합니다.** 지워지는 경우가 (a) 같은 기기에서 교체 (b) 최종 제출 — 둘뿐입니다.
즉 **끝내 제출하지 않은 교사의 임시저장은 영원히 남습니다.** 마감이 지나도요.
게다가 브라우저를 바꾸면 새 키가 발급되어 **이전 draft는 고아가 되어 영구 잔존**합니다. 소유자도 담당자도 열 수 없고 지울 수도 없으며, **아무도 인지조차 못 합니다.**

> 실측: 김민정 교사 = 3분 시연에 **버전 3개**, 22,944바이트 HWPX 3개(전부 같은 크기 = 사실상 중복).
> 추산: 교사 50명 × 재제출 3회 × 200KB = **요청 1건당 30MB.** 연 50건이면 1.5GB가 전부 삭제 불가.

**⚠️ 버전 불변 보관 자체는 좋은 설계입니다.** *"내가 낸 건 A인데 왜 B가 갔냐"* 분쟁에서 증거가 됩니다. **없애자는 게 아닙니다.**

**💬 "무기한 보관"이 아니라 "정해진 기간 동안 불변 보관"으로 정리하는 것이 어떨까요.**

함께 정해야 할 것: 요청 전체 삭제 / 개별 버전 삭제 허용 여부 / 감사 목적 보존 범위 / 마감 후 임시본 자동 파기 / 기본 보존기간과 연장 / 삭제 로그와 실제 파일 정합성.

> **법률 관련:** 개인정보의 목적 달성 후 보관은 문제가 될 수 있지만, **학교 기록물 보존 의무와 충돌할 수 있어** 제가 단정할 사안이 아닙니다. **운영 전 기관 개인정보 담당자 확인이 필요합니다.**

### 3-7. 마감 후에도 임시저장이 됩니다 (코드 확인)

최종 제출은 마감을 **두 번** 검사하는데(좋습니다), **임시저장 라우트 2개에는 마감 검사가 0건**입니다.

```
draft/route.ts        → assertCollectionOpen 0건
table-draft/route.ts  → 0건
submissions/route.ts  → 3건  ← 비교군
```

마감 후에도 저장공간 소비와 "작성 중" 상태 조작이 가능합니다.

**💬 정책 질문:** 마감은 **제출만** 막는 것인가요, **모든 작성**을 막는 것인가요?
후자라면 모든 쓰기 API에 같은 검사가 필요합니다.

### 3-8. 공용 PC에서 남의 문서가 열립니다

복구 키가 `localStorage`에 평문 저장됩니다(`school-work-draft:{token}:{teacherId}`).

**학교의 표준적 사용 패턴에서 바로 발생합니다:**
1. 교사 A가 교무실 공용 PC에서 작성 중 임시저장하고 나감
2. localStorage는 그대로 남음
3. 다음 사용자가 같은 브라우저로 그 링크를 엶
4. **키가 자동 재사용되어 A의 문서가 편집기에 그대로 열림**

XLSX는 더 직접적입니다 — 임시 파일 다운로드 링크가 그대로 렌더링됩니다.

**💬 `sessionStorage`로 바꾸면 "브라우저 껐다 켜도 복구"라는 가치가 사라집니다.** 그래서 순서를 제안하면:
1. **복구 전 "○○○님의 임시저장본을 불러올까요?" 확인** ← 이것만으로 대부분 해결
2. "이 기기에서 복구 정보 삭제" 기능
3. 복구 키 만료

### 3-9. URL에 비밀정보가 들어 있습니다

관리 토큰·제출 토큰이 **URL 경로**에, 복구 키가 **쿼리 문자열**에 있습니다.

브라우저 기록, 프록시·서버 로그, 화면 공유, Referer에 남을 수 있습니다.
특히 관리 페이지에서 같은 origin의 다른 페이지로 이동하면 **전체 관리 URL이 Referer로 기록될 가능성**이 있습니다.

**💬 관리 토큰은 최초 교환 후 `HttpOnly`·`Secure`·`SameSite` 세션 쿠키로 전환하고 URL에서 제거하는 편이 안전합니다.**

### 3-10. HTTPS와 보안 헤더

`next.config.ts`가 **사실상 비어 있습니다** (확인 완료). CSP·Referrer-Policy·frame 제한·HSTS·전역 `nosniff` 없음.
실행 안내도 HTTP 기반이라 **내부망에서도 토큰과 문서가 평문으로 오갑니다.**

## 4. C. 운영 단계 — 나중에

### 4-1. ⛔ PostgreSQL은 "어댑터만 만들면" 되는 상태가 아닙니다

README에 *"뼈대는 있고 어댑터는 다음 단계"*라고 하셨는데, **`src/db/schema.ts`에 웹 표에 필요한 컬럼이 통째로 없습니다:**

- `collections`에 `type` 없음 → document/table/xlsx 구분 불가
- `collections`에 `table`(열 정의) 저장할 곳 없음
- `submission_versions`에 `kind`·`rows` 없음 → **표 제출 데이터를 못 담음**
- `storage_key`가 `.notNull()`인데 표 제출은 `storageKey:""`를 씀

**스키마가 웹 표 기능 추가 전에 만들어지고 갱신되지 않았습니다.**

→ 이걸 모르고 착수하면 담당자가 막힙니다. **스키마 재설계부터** 해야 합니다.

**⛔ 그리고 이틀 안에는 절대 손대지 마세요.** `Collection`이 `recipients[].versions[].rows[]`까지 깊게 중첩된 단일 객체라 관계형으로 풀면 4개 테이블 조인 + 트랜잭션 재설계입니다. **여러 명이 작업하는 이틀 동안 저장 계층을 바꾸면 나머지 전부가 블로킹됩니다.**

### 4-2. 직렬 큐는 단일 프로세스 전제입니다

`createSerialQueue()`가 모듈 스코프 변수라, 프로세스를 여러 개 띄우면(PM2 cluster 등) **프로세스 간 상호배제가 없어 제출이 조용히 유실됩니다.**

현재 `Dockerfile`은 단일 프로세스라 안전하지만 **우연히 안전한 것**입니다.
→ **"동시 제출에 안전하다"고 일반화하면 안 됩니다.** 최소한 코드에 주석이라도 남기는 게 좋겠습니다.

### 4-3. 감사 로그가 비어 있습니다

`db/schema.ts`에 `auditEvents` 테이블이 정의돼 있으나 **쓰는 코드가 0줄**입니다.
→ "감사 추적 가능"이라고 말하면 안 됩니다. 실제로 남는 건 제출 버전 이력뿐입니다.

### 4-4. 그 밖

의존성 취약점 6건(moderate) — `drizzle-kit` 하위 `esbuild`, `exceljs` 하위 `uuid`.
특히 esbuild 권고는 **개발 서버가 악성 사이트 요청에 노출**될 수 있는 유형인데, 이 앱은 시연에서도 `next dev`를 씁니다.

미사용 의존성 3개 제거 가능: `archiver`(ZIP은 fflate로 처리 중), `@rhwp/core`(editor만 import), `postgres`(연결 코드 없음). 폐쇄망 설치 시 불필요한 다운로드입니다.

## 6. 시연 전략

### 가장 강한 것: 웹 표 취합

**순서:**
1. 담당자가 열 정의 (글자/숫자/날짜/단일선택, 필수, 순서 이동)
2. 링크 복사
3. 교사 A: 이름 선택 → 행 입력 → **새로고침** → 복구되는 것 시연
4. 교사 B도 제출
5. 담당자: **`통합 XLSX 다운로드` 한 번**
6. 열어보면 — **헤더 고정, 자동필터, 열 너비 자동, 남색 헤더**까지 적용

**6번이 인상 포인트입니다.** "CSV 뱉는 것"과 "열어서 바로 쓸 수 있는 엑셀"의 차이는 실무자가 즉시 알아봅니다. 숫자 열은 실제 숫자 타입이라 SUM이 바로 됩니다.

또 하나: **제출 현황 시트.** 취합 결과와 미제출자 명단이 **같은 파일 한 장에** 있습니다.
부장 입장에서 *"이거 그대로 교감한테 올린다"*가 됩니다.

### 반박하기 어려운 지점

1. **"HWP를 브라우저에서 연다"** — 구글드라이브도 MS365도 못 합니다. *"그거 이미 있잖아요"*에 대한 가장 강한 답
2. **"작성 중은 보이는데 내용은 안 보인다"** — 코드로 보장되고 화면에 정책 명시. 대안에 없는 조합
3. **"제출 이력이 지워지지 않는다"** — 분쟁 시 증거
4. **"테스트가 있고 통과한다"** — 그 자리에서 `npm test`. **0.4초.** 해커톤에서 이걸 보여줄 수 있는 팀은 소수
5. **"서버엔 토큰 해시만 있다"** — `state.json`을 열어 `shareTokenHash`만 있는 걸 보여주면 강력
